# tokideliと類似機能を持つコマンドとの優位性比較 ― 車輪の再発明をした理由

(English version is [here](tokideli_vs_simillar_products.info.en.md))

tokideliの各コマンドの中には、既存の有名なコマンドと類似の機能を持つものがいくつかある。よって「それがやりたくば、既存のコマンド『○○』を使えばいい。なぜ車輪の再発明をしてコマンドを乱造するのか」という指摘を受けることもある。しかし、我々がコマンドを作った理由は、既存のそれらコマンドに対して、品質や機能、さらには欠陥が見受けられるという不満を抱いたからである。この文書では、実際に再発明だと指摘を受けたtokideliコマンドと、類似の機能をもつ既存コマンドを比較し、それぞれについて再発明した意義を記していく。

## `valve` vs [pv](https://www.ivarch.com/programs/pv.shtml)の`-L`オプション

データ転送レートを一定に制限したいなら、[valve(1)](valve.man.ja.md)コマンドなど作らずとも、有名な[pv](https://www.ivarch.com/programs/pv.shtml)コマンドの`-L`オプションを使えばいいという指摘がある。

しかし我々に言わせれば、「`pv -L`はとにかく精度が低くて荒い」という一言に尽きる。`pv` 1.11.0のソースコード（`src/pv/loop.c`、`src/pv/transfer.c`）を調べると、`-L`は100ミリ秒単位でしか送信可能量を更新しない離散的なトークンバケット方式であり、かつその送信可能量の検知自体も90ミリ秒固定のタイムアウトを持つ`select()`のポーリングに依存している。この互いに協調しない2つの粗い周期が、うなり（ビート）のようなジッターを生む。

一方`valve`は、次に送出すべき絶対時刻を直接計算して`nanosleep()`する方式であり、誤差が蓄積しない。実測では、1行/秒のレートにおける間隔の標準偏差が`valve`で0.288ms、`pv -L`で3.573msと、一桁近い差が出た。この設計上の違いと実測データの詳細は、[valveコマンドの転送レート精度に関するレポート](valve_precision.info.ja.md)にまとめてある。

### 総評

`pv`は、パイプを通り抜けるデータの流れ具合を可視化するという、進捗モニタリングが本来の機能であるように見える。`-L`によるレート制限は、その本来機能に付随するオマケ的な位置づけなのではないか。だとすれば、精度がさほど重視されていないのも納得できる。

## `delay` vs [rom1v/delay](https://github.com/rom1v/delay)

tokideliの[delay(1)](delay.man.ja.md)に対しては、ほぼ同様の機能を持ち、しかも同一の名前を持つ[rom1vのdelay](https://github.com/rom1v/delay)があるのに一体何が不満なのかという指摘を受けた。確かにどちらも「標準入力から到来したデータを一定時間遅延させてから標準出力へ送る」という同じ目的を持つが、次に記す三つの点で若干の物足りなさを感じていた。

* **性能・設計面**: rom1v版`delay`は、タイムスタンプ付きの「チャンク」（最大4000バイト）単位でリングバッファに格納する方式であり、ミリ秒精度・チャンク粒度のタイムスタンプしか持てない。一方tokideli版`delay`は、1バイトごとに個別のナノ秒精度タイムスタンプを記録する。ただしこの精度を得る代償としてtokideli版`delay`は、バッファーに保持可能なデータサイズに対してメモリ消費量が約16倍に達するという短所がある。
* **機能面**: rom1v版`delay`はバッファが満杯になると常に読み込みをブロックするのに対し、tokideli版`delay`は`-o`（上書き）・`-d`（切断）といった複数のあふれ処理モードを持ち、`controlfile`機構により実行中でも遅延時間・バッファサイズを変更できる。一方rom1v版`delay`にはこれらの手段がない。
* **移植性**: rom1v版`delay`は単一目的に特化した5ファイル構成の小さなツールで、2019年5月を最後に活発な開発が止まっている。GitHub上には、ヘッダー構造体へのポインタをアライメント未保証の位置にキャストしてアクセスしている箇所が未定義動作であるという、未解決のissueも残っている。tokideliの`delay.c`は単一ファイルで完結し、Linux・Solaris・FreeBSD・NetBSD・OpenBSD・macOS・Android上のLinuxという7環境での動作を確認している。

これらの詳細は、[tokideliのdelayコマンドと先行するdelayコマンド（rom1v/delay）の比較](delay_commands_comparision.info.ja.md)に詳しく記したので、そちらを参照されたい。

### 総評

rom1v版`delay`は、メモリ効率が良く理解しやすい反面、運用面の柔軟性やタイムスタンプの精度には乏しい。tokideli版`delay`は、バイト単位・ナノ秒精度と運用中の柔軟性を獲得した代償として、メモリ消費量が増えている。メモリ消費量を節約したいか、高い精度を重視したいか、また、機能や移植性を重視したいかといった要求に応じてどちらがより適しているかが異なる。そして私達は、高い精度と移植性が欲しかった。

## `linets`/`charts` vs `ts`（[moreutils](https://github.com/pgdr/moreutils)）

データの到来時刻に対して行単位でタイムスタンプを付与したいなら[moreutils](https://github.com/pgdr/moreutils)に含まれる`ts`コマンドがあるので[linets(1)](linets.man.ja.md)コマンドなど不要という指摘があるが、`ts`コマンドに対してもいくつか不満があった。

まず、`ts`コマンドはPerlで実装されている。Perlを古い言語と見なし、その導入自体を嫌う声があるからか、[Goで書かれた非公式のmoreutils実装](https://github.com/sweetbbak/go-moreutils)すら登場しているほどである。実際、スピードの遅さも否めない。次のワンライナーで同じ処理（10万行への行頭タイムスタンプ付与）をさせて比較したところ、`ts`は`linets`に対しておよそ2倍近い時間を要した。

```sh:
$ time yes | head -n 100000 | ts %.s     > /dev/null
$ time yes | head -n 100000 | linets -6e > /dev/null
```

（本ドキュメント執筆時点の検証環境での実測、3回の平均的な値）

|      | `ts %.s` | `linets -6e` |
|------|---------:|-------------:|
| real |    0.88s |        0.46s |
| user |    0.28s |        0.09s |
| sys  |    0.59s |        0.37s |

実時間（real）でおよそ1.9倍、ユーザーCPU時間（user）だけで見るとおよそ3倍の差があり、Perlインタプリタが行ごとに払っている処理コストの重さがうかがえる。

機能面では、次のような違いがある。

* 出力フォーマットの柔軟性という点では、`ts`に特に不満はない。カレンダー日時・UNIX時間・拡張ISO 8601形式での出力など[linets(1)](linets.man.ja.md)や[charts(1)](charts.man.ja.md)で出力可能なフォーマットのほぼすべてを`ts`で設定できる。`ts`で対応していないのはナノ秒単位での出力であるが、現在の一般的なPCやOSで得られる精度を踏まえれば現実的といえる。
* `ts`の`-s`（プログラム起動時からの経過時間モード）は、`linets`の`-z`に相当する。しかし、`linets`の`-Z`（テキストデータの1行目到来時点からの経過時間）に相当するモードは`ts`にはない。
* `linets`は行の**先頭文字**が到来した時刻をタイムスタンプにするが、`ts`は行末（改行またはEOF）到来時刻でタイムスタンプを打つ。
* `ts`で`-i`（直前行のタイムスタンプからの経過時間）を選ぶと出力は差分のみになり、絶対時刻と差分を同時に出力することはできない。`linets`の`-d`オプションは、1列目に絶対時刻、2列目に直前行からの経過時間を両方同時に出力できる。
* `ts`は`-m`オプションでMONOTONIC時計を使うモードを選べるが、`-m`指定時でも出力自体は結局実時刻（カレンダー時刻またはUNIX時間）形式に変換されて表示される。つまり、MONOTONIC時計で測った経過時間を、起動時に取得した基準実時刻に加算して表示しているだけであり、実行中にシステム時刻が修正されると、表示される絶対時刻自体はその修正を反映しない。したがって、カレンダー日時・UNIX時間・拡張ISO 8601形式のような絶対時刻表示との組み合わせでは、`-m`を選ぶ意味は薄い。`linets`では、絶対時刻形式（`-c`・`-e`・`-I`）の時はREALTIME時計、経過時間形式（`-z`・`-Z`）の時はMONOTONIC時計を、オプションの意味に応じて自動的に選択している。
* `ts`でできるのは行単位のタイムスタンプ付加のみであり、文字単位・バイト単位の記録は単独ではできない。どうしてもやりたければ、テキストデータを事前に1文字1行へ加工しておく必要があるが、その加工処理をしている間に時間が経過してしまい、到来タイミングの記録という目的そのものが崩れてしまう。`charts`であれば、この加工処理を挟まずに文字単位のタイムスタンプを直接記録できる。

### 総評

`ts`はやや時代遅れ感の否めないPerlで実装されており、導入自体を敬遠されることがあるうえ、動作も遅い。一方`linets`/`charts`はPOSIX Cで書かれており、導入の障壁が低く、しかも速い。機能面でも`ts`は`linets`/`charts`に比べてやや限定的で、絶対時刻と差分の同時出力ができなかったり、何より文字単位の記録ができない。確かに`ts`はタイムスタンプフォーマットを`strftime`書式で指定できる点では柔軟性があるが、フォーマット変換自体は`sed`等の別のテキスト処理コマンドに任せればよいように思う。

## `charts`/`linets`/`tscat` vs [asciinema](https://asciinema.org/)

[asciinema](https://asciinema.org/)は素晴らしいツールである。ターミナル画面の操作の様子を録画・再生でき、しかもデータはテキスト形式（JSON Lines、拡張子`.cast`）なので軽量だという特長もある。

ただし、`asciinema`の`.cast`形式は、あくまで`asciinema`自身で利用することを前提とした内容・形式である。テキスト形式ではあるものの、各行は`[time, type, data]`という形のJSON配列であり、`data`部分はJSON文字列としてエスケープされている。したがってテキストとして人間が読むことはできるが、`grep`や`sed`のような汎用テキスト処理コマンドで直接加工するのは難しく、まずJSONパーサーを介する必要がある。

我々が欲しかったのはもっと汎用的なもの、つまり標準入出力を流れるデータそのものの流れをコントロールするための道具である。[charts(1)](charts.man.ja.md)・[linets(1)](linets.man.ja.md)・[tscat(1)](tscat.man.ja.md)が取り扱うタイムスタンプ付きテキストは、JSON配列としての構造を持たない代わりに、`grep`・`sed`・`awk`など通常のUNIXテキスト処理コマンドにそのまま通せる。

ただし、`.cast`形式とtokideliが出力する形式は、（冒頭に記録されている画面サイズ等のメタデータを除けば）理論上は相互変換可能である。実際、`charts`/`linets`の`-j`オプションが生成する「タイムスタンプ + JSONエスケープ済みペイロード」という1行の構造は、`.cast`の`[time, type, data]`というJSON配列の各要素とほぼ1対1に対応する。将来的には、この相互変換を行うツールも用意したいと考えている。

### 総評

`asciinema`とtokideliのこれらのコマンドは、どちらが優れていて、どちらを使うべきかを競うような関係にはない。`asciinema`はターミナル画面操作の録画・再生に特化しているのに対し、`charts`/`linets`/`tscat`は標準入出力の流れそのものを記録・再生するという汎用性を追求している。両者はデータを相互変換できるようにして、むしろ友好関係を築くべき間柄だと考えている。

## `ptw` vs `unbuffer`（[expect](https://sourceforge.net/projects/expect/)）

[ptw(1)](ptw.man.ja.md)は、GNU coreutilsにある[stdbuf(1)](https://www.gnu.org/software/coreutils/manual/html_node/stdbuf-invocation.html)を使ってもフルバッファリングモードを行バッファリングモードに変えられない場合でも効果を発揮する（可能性が高い）コマンドとして製作したが、そんなことは[expect(1)](https://sourceforge.net/projects/expect/)コマンドに付属する`unbuffer`コマンドでできるという主張がある。しかし以下に示すように、`unbuffer`は話にならないほど出来が悪い。

### 起動・処理のオーバーヘッド

まず`unbuffer`はTclスクリプト（`expect_unbuffer`）として実装されているので起動コストが大きい。試しに次のワンライナーで1行だけのデータを処理させて起動から終了までの時間を測ると、`unbuffer`は`ptw`のおよそ5〜10倍の時間を要した（本ドキュメント執筆時点の検証環境での実測、3回の平均的な値）。

```sh:
$ time echo x | unbuffer -p cat > /dev/null
$ time echo x | ptw cat > /dev/null
```

|      | `unbuffer -p cat` | `ptw cat` |
|------|------------------:|----------:|
| real |           約0.02s |  約0.003s |

### バグ1: 上流コマンドが終了すると、未処理データを残したまま終了する

次のワンライナーで、`seq`コマンドが生成する4000行を`tr`コマンド経由で中継させてみる（ここで中継役に`tr 1 1`を選んだのは、入出力データは一切変化させずにバッファリングモードの変化のみを観察するためである）。

```sh:
$ seq 4000 | unbuffer -p tr 1 1 | cat > with_unbuffer.txt
$ seq 4000 | ptw tr 1 1         | cat > with_ptw.txt
```

`ptw`は`seq`によって生成された4000行を約9msで出力した。一方で`unbuffer`は実行のたびに出力される行数が変わるが、いずれにしても4000行には遠く及ばない行数（実測では21行程度）しか出力されず、しかも処理自体はごく短時間で終了してしまう。

原因は、`unbuffer -p`の実装（`expect_unbuffer`内の`interact`呼び出し）が、上流コマンドの標準入力側がEOFになった瞬間、`tr`からの出力をわずかに待つだけ（`expect -timeout 1 -re .+`）で処理を打ち切ってしまうという仕様による。`seq`のようにデータを一瞬で出力し終える上流コマンドと組み合わせると、`unbuffer`内部の中継処理がまだ大半のデータを処理し終えていない段階で上流がEOFになり、残りのデータは中継されないまま失われる。

### バグ2: 大量データ転送中に、レースコンディションでフリーズ・データ消失する

上流の終了を人為的に遅らせれば（例: `(seq 4000; sleep 5) | unbuffer -p tr 1 1 | cat`のように末尾に`sleep`を挟む）、バグ1は回避できる。ところが、さらに別の欠陥に見舞われる。

本ドキュメント執筆に用いた検証環境でこの回避策を使って`seq 4000`を試したところ、ある実行回では840行しか出力されないまま（それでも終了コード自体は正常に）終了し、別の実行ではプロセスが完全にフリーズし、強制終了が必要になった。

この原因を`strace`を使って追跡したところ、`unbuffer`本体（tclshプロセス）のシステムコール列に、次のような特徴的なパターンが見られた（fd0=標準入力、fd3=子プロセス`tr`へのpty）。

```text:
read(0, ...)
write(3, "...", 4096)        # ← ここまでは正常に中継されている
write(3, "...", 1905)
read(0, ...)
write(3, "...", 4096)
write(3, "...", 1905)
read(0, ...)
write(3, "...", 2417)        # ← 最後のpty書き込み
read(0, <unfinished ...>)    # 以降、write(3, ...)が一切出ない
read(0, <unfinished ...>)
read(0, "...", 4096) = 4096  # 読めているのに書き込まない
read(0, <unfinished ...>)
# → このままブロックし続ける
```

つまり、`interact`の内部ループは「読めるうちはとにかく読み続け、書き込みは後回しにする」という実装になっており、読んだデータをpty側へ書き込まずに溜め込んだまま次の`read()`を呼び続けることがある。この「読みっぱなし」状態のまま、たまたま上流パイプが一瞬空になるタイミングで`read(0, ...)`を呼んでしまうと、そのシステムコールは次にデータが来るまでブロックしてしまい、すでに読み込み済みだが未転送のデータは`tr`に届かないまま取り残される。

これはカーネルのバッファサイズ等、何らかの上限に達することで決定的に起こる現象ではない。`read`と`write`のどちらが呼ばれるかは、上流パイプへのデータ到着タイミングとOSのスケジューリングに依存する**レースコンディション**であり、データ量が多くなるほど（＝`read`の呼び出し回数が増えるほど）、運悪く読み出しブロックが生じてしまう確率が上がる。

これが、`unbuffer`に大量データを処理させるとデータ消失やフリーズが起こる原因である。

### バグ3: 標準出力と標準エラー出力が混合される

[Hacker Newsのあるコメント](https://news.ycombinator.com/item?id=42401011)で、`unbuffer`は標準出力と標準エラー出力を混合してしまうという指摘があったが、その通りだった。

次のようにして`tee`コマンドで標準入力から得られたデータを標準出力・標準エラー出力にしようすると、`unbuffer`ではどちらも標準出力に出てきてしまう。

```sh:
$ echo foo | ptw         tee /dev/stderr | sed 's/.*/stdout: &/'
foo
stdout: foo
$ echo foo | unbuffer -p tee /dev/stderr | sed 's/.*/stdout: &/'
stdout: foo
stdout: foo
$ 
```

原因は実装方式の違いにある。`unbuffer`（Tcl/Expectの`unbuffer`スクリプト）は内部で`spawn`コマンドを使って対象プロセスを起動しているが、Expectの`spawn`は仕様上、子プロセスの標準出力と標準エラー出力の両方を同じ1つの擬似端末（PTY）に結合してしまう。これは`unbuffer`固有のバグというより、Expectの`spawn`自体の制約に起因するものである。対して`ptw`は、標準出力だけをPTYスレーブに繋ぎ、標準エラー出力には一切手を加えない設計になっている。そのため標準エラー出力は呼び出し元から継承されたファイルディスクリプタのままPTYを経由せず、標準出力とは完全に独立した経路を保てる。

### 総評

`unbuffer`は、`ptw`とどちらが優れているかを比較するに値しない。起動コストの高さという性能面の弱点に加え、「上流終了時に未処理データを残して打ち切る」「大量データ転送中にレースコンディションでデータ消失・フリーズする」「標準出力と標準エラー出力が混合される」という3つの致命的なバグを抱えており、信頼して使えるツールではない。

## `ptw` vs `pipetty`（[colorized-logs](https://github.com/kilobyte/colorized-logs)）

[ptw(1)](ptw.man.ja.md)と`unbuffer`の検証結果を説明すると、ある者は「それなら[colorized-logs](https://github.com/kilobyte/colorized-logs)に収録されている`pipetty`を使えばいい」と指摘をしてくる。しかし`pipetty`もまた、いくつかの問題点や不満に思える点を抱えている。

### 標準出力と標準エラー出力が混合される

`pipetty`のソース（`pipetty.c`）を見ると、次のように標準出力と標準エラー出力の両方を同じPTYスレーブに繋いでいる。

```c:pipetty.c
dup2(slave, 1);
dup2(slave, 2);
```

これは前述の`unbuffer`と同じ問題である。`unbuffer`と同様の`tee`コマンドを使った実験をすれば、`pipetty`においても標準出力と標準エラー出力が混ざる様子がわかる。

```sh:
$ echo foo | ptw     tee /dev/stderr | sed 's/.*/stdout: &/'
foo
stdout: foo
$ echo foo | pipetty tee /dev/stderr | sed 's/.*/stdout: &/'
stdout: foo
stdout: foo
$ 
```

しかしわざわざ同じPTYに繋がなければ混ざらないのに、それをあえて行っているということは仕様なのかもしれない。しかしいずれにせよ、この問題（または仕様）によって、混合を望まないユーザーに対しては不都合な結果をもたらす。

### PTYを無条件に確保する

`ptw`は、自分自身の標準出力が既に端末に接続されている場合（パイプラインの末端で直接ターミナルに出力するような場合）、PTYを確保せずそのまま`exec()`するショートカットを持つ（`-f`オプションで強制上書き可能）。端末に直接繋がっているなら、PTYで騙す必要がそもそもないからである。一方、`pipetty`にはこの判定が無く、常にPTYを確保する。よって`pipetty`は不要な起動コストを払う場合がある。

### 大量データ転送時の性能

次のようにして大量データを`tr`経由で中継する処理で比較したところ、（筆者の検証環境の）Linuxでは`ptw`の方がわずかに速かった（1億行、複数回の平均的な値）。

```sh:
$ time yes | head -n 100000000 | ptw     tr 1 1 | cat > /dev/null
$ time yes | head -n 100000000 | pipetty tr 1 1 | cat > /dev/null
```

|      | `ptw`   | `pipetty` |
|------|--------:|----------:|
| real | 約1.34s |   約1.43s |

なお、この性能差はLinux特有のもののようで、いくつかの他のUNIX系OS（FreeBSD 12.1・Solaris 11.3・macOS 15.8）で試しても有意な速度差は見られなかった。

調査の結果、この速度差が生じる理由は、`ptw`と`pipetty`でPTYスレーブに設定するtermios属性が若干異なること、そしてその違いによってLinuxカーネル内で異なるコードパスを通ることであるとわかった。具体的な場所は、Linuxカーネルソースコードの一つ`drivers/tty/n_tty.c`内の`n_tty_write()`である。

`ptw`ではtermiosの`OPOST`属性をONのままにしている一方、`pipetty`ではOFFにしているが、`n_tty_write()`は`OPOST`の有無でコードパスが分岐している。`OPOST`がONの時だけ使われる`process_output_block()`は書き込み前に空きバッファ量（`tty_write_room()`）を確認してから書き込む一方、`OPOST`がOFFの時は空き容量を確認せず`pty_write()`を直接・無条件に呼ぶ。後者の経路の方がこの環境では`voluntary context switches`が多くなり、結果としてCPU使用時間（sys）は減るのに全体の所要時間（real）は増える。試しに`ptw`における`OPOST`属性をOFFにしたものと`pipetty`とで動作速度を比較すると、ほぼ同一の所要時間になった。

|                            | `ptw`原版<br>(OPOST ON) | `ptw`(OPOST OFFのみ変更) | `pipetty`実物 |
|----------------------------|------------------------:|-------------------------:|--------------:|
| real（1億行、3回平均）     | 約1.34s                 | 約1.47s                  | 約1.43s       |
| sys                        | 約2.06s                 | 約1.78s                  | 約1.72s       |
| voluntary context switches | 約65,200                | 約82,100                 | 約80,350      |

### 総評

`pipetty`はC言語で実装されており、起動のたびにTclインタプリタを起動する`unbuffer`と比べればはるかに軽量である。しかし、`unbuffer`と同じ「標準出力と標準エラー出力が混合される」という問題を抱えている点、PTYを無条件に確保してしまう点、そして大量データ転送時の性能がわずかに`ptw`に劣る点で、`ptw`に一定の優位性がある。

## `ptw` vs `script`

`ptw`には他にも商売がたきがいるようで、ある者は「`script`コマンドを使えばいいじゃないか」と言う。しかし実際に検証してみると、`script`もまた`stdbuf`コマンドの代替品として使うにはまったく向いていないということがわかった。

### 利点: 追加インストールが不要

はじめに一つ、`script`コマンドにある強力な利点を述べておく。それは、このコマンドがほぼすべてのUNIX系OSに標準で入っているという点である。導入の障壁という点で`script`、`unbuffer`、`pipetty`、そして`ptw`よりもずっと有利である。

### 問題点1: コマンド書式や機能に互換性の無い複数の`script`がある

`script`コマンドにはBSD版とutil-linux版という少なくとも二種類が存在しており、コマンド書式が異なる。任意のコマンドをラップする場合、BSD版ではラップ対象のコマンド名と引数を`script`コマンドの引数の最後に書き並べるが、util-linux版では`-c`オプションの引数として渡さなければならない。さらに、ローカルエコーを制御する機能が、util-linux版には`-E`というオプションで存在するが、BSD版には無い。

`unbuffer`や`pipetty`でも行った`tee`コマンドによる実験と同じことをやりたければ、util-linux版では次のように書く。

```sh
$ echo foo | script -E never -qec 'tee /dev/stderr' /dev/null | sed 's/.*/stdout: &/'
stdout: foo
stdout: foo  # ← このコマンドも標準出力と標準エラー出力を混合する（後述）
$ 
```

一方、BSD版では例えば次のように書く。ローカルエコーを抑止するために、ラップ対象のコマンド（ワンライナー）の中で抑止するコマンド（`stty -echo`）を付けなければならないし、上流のコマンドはエコー抑止の準備が整うまで`sleep`などで待機しなければならない。しかも上流のコマンドは`script`が処理を終えるまで`sleep`などで終了せずに待機しなければならない。

```sh
$ ( sleep 0.1 ; echo foo ; sleep 0.1 ) | script -qe /dev/null sh -c 'stty -echo; tee /dev/stderr' | sed 's/.*/stdout: &/'
stdout: foo
stdout: foo  # ← BSD版でもやはり標準出力と標準エラー出力が混合される（後述）
$ 
```

`sleep`に与えるべき最小の秒数（特に2番目のもの）は理論的に決められるものではなく、実装やデータサイズ等の要因によって決まるものなので、BSD版`script`はこの目的（`stdbuf`コマンドの代替品）での実用性は極めて低い。

### 問題点2: 標準出力と標準エラー出力が混合される

`script`もまた、`unbuffer`や`pipetty`と同様に標準出力と標準エラー出力を混合するという問題点を持っている。その様子は[問題点1](#問題点1-コマンド書式や機能に互換性の無い複数のscriptがある)で示したコマンド動作結果のとおりである。

### 問題点3: 改行コードがLFからCRLFに変換される

PTYスレーブ側の`OPOST`/`ONLCR`が既定で有効なため、データ中の`\n`はすべて`\r\n`に変換されて出力される。その様子は、`script`からの出力を`cat -v`に通すとわかりやすい。

```sh
# util-linux版
$ echo foo | script -E never -qec 'tee /dev/stderr' /dev/null | sed 's/.*/stdout: &/' | cat -v
stdout: foo^M
stdout: foo^M
$ 

# BSD版
$ ( sleep 0.1 ; echo foo ; sleep 0.1 ) | script -qe /dev/null sh -c 'stty -echo; tee /dev/stderr' | sed 's/.*/stdout: &/' | cat -v
stdout: foo^M
stdout: foo^M
$ 
```

バイナリー一致・`diff`等での比較を前提にするなら、この変換も透過性を損なう問題の一つである。

### 大量データ転送時の性能

`ptw`と`script`（util-linux版）それぞれで次のワンライナーを実行し、`tr 1 1`を経由する100万行の転送にかかる時間を比較した（筆者の検証環境での実測、3回の平均値）。

```sh:
$ time yes | head -n 1000000 | ptw tr 1 1 >/dev/null
$ time yes | head -n 1000000 | script -E never -qec "tr 1 1" /dev/null >/dev/null
```

|      | `ptw`    | `script`（util-linux版） |
|------|---------:|-------------------------:|
| real | 約0.016s |                  約6.32s |
| sys  | 約0.016s |                  約5.79s |

**`ptw`の方が360倍以上速い。**

### 総評

`script`は標準搭載という点で導入障壁は低いが、`ptw`が目指す「`stdbuf`の代替品」という用途には設計上まったく向いていない。それは、util-linux版・BSD版における書式や機能の非互換性、標準出力・標準エラー出力の混合、改行コードのCR+LF化、大幅に劣る処理速度などいくつも理由がある。

## まとめ

ここで取り上げたtokideliの各種コマンドはいずれも、「既存のコマンドに同様の働きをするものが無かった作った」というわけではない。調査の結果、精度・性能・機能・信頼性のいずれかの面でtokideliが目指す水準に届かなかったために、あらためて実装したものである。`pv -L`・`unbuffer`・`pipetty`のように設計・実装そのものに起因する荒さ・欠陥が明確なものもあれば、rom1v/delayや`ts`のように単純な優劣ではなく要求される性能の違いに帰着するもの、そして`asciinema`のように競合ではなく将来的な相互運用を目指すべきものもある。
