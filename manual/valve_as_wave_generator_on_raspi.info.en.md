# Using the valve Command as a Square-Wave Generator on a Raspberry Pi

（日本語版は[こちら](valve_as_wave_generator_on_raspi.info.ja.md)）

The [valve(1)](valve.man.en.md) command "sends data arriving on standard input out to standard output at a constant interval." If you point its output at a real device such as a Raspberry Pi's GPIO, a sequence of data generated purely in software turns directly into a real electrical signal (a pulse train). This document records a hands-on evaluation of how practical that is — in particular, how precise it is as a pulse source for generating a square wave.

## Purpose

To evaluate the quality of the pulses generated by the combination of the `yes` command and [valve(1)](valve.man.en.md). This serves both as an evaluation of its practicality as a pulse source for use as an actual electrical signal, and as material toward evaluating its practicality as a pulse source for use as a timing regulator in software on UNIX.

## Experimental Setup and Equipment

The equipment used in this experiment was as follows.

| Item | Value |
|---|---|
| UNIX machine | Raspberry Pi 3 Model B+ (ARM Cortex-A53, 1.4GHz) |
| OS | Raspberry Pi OS (2021-05-07 release, Linux kernel 5.10.17) |
| Reference pulse generator | Akizuki Denshi Function Generator FG085 |
| Measurement oscilloscope | Hantek DSO4204B (200MHz bandwidth, 4 channels) |

This is intentionally a thoroughly ordinary UNIX environment (affordable, and not a real-time OS), so as to evaluate the quality obtainable in such a setting.

## Method

Square waves of the same frequency are generated from both the Raspberry Pi and the function generator's GPIO output, fed into separate channels of the oscilloscope, and overlaid on its screen. Taking the function generator's waveform as the reference, we observe how precisely the Raspberry Pi's (`valve` command's) waveform lines up with it.

The equipment was connected as shown in the following diagram.

The square wave sent out from the Raspberry Pi is generated with the following one-liner.

```sh:
$ yes 0_1 | tr _ '\n' | valve -l Δt > /sys/class/gpio/gpio2/value
```

`yes` and `tr` alternately generate lines of "0" and "1", which are then passed through the [valve(1)](valve.man.en.md) command. valve writes out "0" and "1" at a constant interval (line-output mode, selected with `-l`, with the interval given by `Δt`) into the GPIO special file, turning them into an electrical signal. Setting `Δt` to, say, 5ms produces a 100Hz square wave (a 10-millisecond period), and likewise setting it to 0.5ms produces a 1kHz square wave.

Varying the value given to `Δt` (i.e., the generated square wave's frequency) produced a noticeably different result at each of the following three settings, so a video was recorded for each.

| Frequency | `Δt` | Video |
|---|---|---|
| 100Hz | ≈ 5ms | <https://youtu.be/e8Qx46Gbz-s> |
| 1kHz | ≈ 0.5ms | <https://youtu.be/1WZZLyjXYvg> |
| 10kHz | ≈ 50us | <https://youtu.be/a-X0ydGcugY> |

At 100Hz (`Δt`≈5ms), the two waveforms stayed almost perfectly overlaid throughout. At 1kHz (`Δt`≈0.5ms), they also stayed essentially well overlaid, though roughly once every ten-odd seconds a momentary phase shift of about 0.1 wavelength was observed. Jitter of this magnitude should be well within the range a real-time control loop could absorb as a disturbance.

At 10kHz (`Δt`≈50us), however, the square waves could no longer be kept stably overlaid; they continuously drifted back and forth along the time axis by roughly ±0.1 to 0.2 wavelength. In other words, even when `Δt`≈50us was specified, an error of roughly ±10us was always present — a sign that we had hit the limit of the timing precision reproducible on a Raspberry Pi 3 Model B+.

Note that this document deliberately writes "`Δt`≈ XX" rather than "`Δt`= XX." That is because, for example, setting `Δt` to 5ms did not actually yield a precise 100Hz square wave; 5.003ms had to be specified to achieve that in practice. This is presumably due to the precision and unit-to-unit variation of the oscillator built into the Raspberry Pi (the clock period of a low-cost oscillator is also affected by ambient temperature).

## Discussion

The main cause of the irregular time-axis wobble (jitter) that becomes visible from around 1kHz upward is that an ordinary UNIX-like OS, being multi-user and multi-tasking, is interrupted at irregular intervals. Real-time OSes, including RTLinux, exist precisely to avoid this problem. On the other hand, **at frequencies up to around 1kHz, even an affordable UNIX host like a Raspberry Pi has a certain degree of practical utility while running a non-real-time OS.**

## Summary

* Simply combining the `yes` command with [valve(1)](valve.man.en.md) and writing the output to a Raspberry Pi's GPIO special file is enough to generate a square wave (pulse train) with practically useful precision.
* From around 100Hz up to about 1kHz, the waveform obtained was stable to a degree comparable with a dedicated pulse generator.
* At 10kHz, the software-level constraints of a non-real-time OS on a general-purpose UNIX host produce a constant jitter of roughly ±10us, and a stable waveform can no longer be maintained.
* Therefore, when using [valve(1)](valve.man.en.md) as a pulse source for an electrical signal, or as a timing regulator within UNIX, a good practical rule of thumb is to keep frequencies to around 1kHz or below.
