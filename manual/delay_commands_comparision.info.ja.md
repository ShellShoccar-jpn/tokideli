# tokideliのdelayコマンドと先行するdelayコマンド（rom1v/delay）の比較

`delay`という名前の似たコンセプトを持つコマンドが、tokideli以前から存在していたことが分かりました（[rom1v/delay](https://github.com/rom1v/delay)）。両者とも「標準入力から到来したデータを、一定時間遅延させてから標準出力へ送る」という同じ目的を持っていますが、実装を比較すると設計思想がかなり異なることが分かったので、ここに記録します。

(English version is [here](delay_commands_comparision.info.en.md))

## バッファサイズの意味の違い

これが今回の調査の出発点になった疑問です。結論としては、**両者の「バッファサイズ」は意味が異なります**。

### rom1v/delay: タイムスタンプ込みの「チャンク」全体のバイト数

rom1v/delayの`dtbuf.c`を読むと、リングバッファは単純な`char *data`のバイト配列で、そこに「チャンク」という単位でデータを書き込みます。1チャンクは次のような構造です（`dtbuf.c`より）。

```c
struct header {
    time_ms timestamp;      /* int64_t */
    chunk_length data_length; /* uint16_t */
};
#define DTBUF_CHUNK_PAYLOAD_SIZE 4000
#define DTBUF_CHUNK_SIZE (sizeof (struct header) + DTBUF_CHUNK_PAYLOAD_SIZE)
```

つまり、1回のチャンク書き込みで、ペイロード4000バイトの**手前に**タイムスタンプ用ヘッダー（`int64_t`+`uint16_t`で、通常のアライメントでは16バイト程度）が書き込まれます。`-b`で指定した`capacity`バイトは、このヘッダー+ペイロードのペアを格納するための領域として丸ごと使われます（`dtbuf_init()`が確保する実サイズは`capacity + DTBUF_CHUNK_SIZE - 1`ですが、この上乗せ分は「リングバッファの境界でチャンクが分断されないようにする」ための末尾の余白であり、タイムスタンプのための恒常的な追加確保ではありません）。

したがって、**指定した`-b`バイト数の中に、データ本体とタイムスタンプが共存**しています。ただし、1チャンクあたりの実質的なオーバーヘッドは「ペイロード4000バイトに対してヘッダー16バイト程度」、つまり約0.4%に過ぎず、実用上はほぼ無視できる差です。READMEにある「dtbufsize is the buffer size storing the data」という説明は、厳密には「タイムスタンプ付きのデータを格納するための総バイト数」であり、多少簡略化されていると言えます。

### tokideliのdelay: タイムスタンプは指定サイズの外側

一方、tokideliの`delay.c`は、`ringelem_t`という「1バイトのデータ + その到着時刻（ナノ秒精度）」を持つ構造体の配列としてリングバッファを実装しています。

```c
typedef struct _ringelem_t {
  unsigned char ucData;      /* 受信したバイトそのもの */
  uint32_t      u4Nsec;      /* 到着時刻の小数秒部分（ナノ秒、0-999999999）*/
  time_t        i8Sec;       /* 到着時刻の整数秒部分 */
} ringelem_t;
```

タイムスタンプを`struct timespec`のまま持たせず、`uint32_t`（ナノ秒は0〜999,999,999にしか収まらず32bitで十分）と`time_t`に分けたうえで、1バイト→4バイト→8バイトという、アライメント要求が小さい順にフィールドを並べることで、構造体のパディングを最小限に抑えています。

`size`引数（例: `100MiB@1s`の`100MiB`部分）は、この構造体の**要素数**、つまり「純粋なデータバイト数」を表します。実際に確保されるメモリ量は`sizeof(ringelem_t) * size`となり、64bit環境では1要素あたり16バイトになります（`struct timespec`をそのまま使っていた場合は24バイトになるところを、上記の工夫で33%削減しています）。つまり、指定した`size`の**外側に**、その15倍前後の追加メモリがタイムスタンプ保持のために確保されています。

### なぜ違うのか: 記録の粒度の違い

この違いは実装上の癖ではなく、両コマンドが解決している問題の「粒度」が異なることに起因しています。

- rom1v/delayは、`poll()`で検出できた分のデータをまとめて最大4000バイトの「チャンク」単位で読み書きします。1チャンク内の全バイトは同じ1つのタイムスタンプ（ミリ秒精度）を共有するため、タイムスタンプの記録コストはチャンクあたり1回で済みます。
- tokideliのdelayは、1バイトごとに個別のナノ秒精度の到着時刻を記録し、バイト単位で正確に遅延時間を計算します。この精度を得るために、バイトごとにタイムスタンプを持たせる必要があり、結果としてメモリオーバーヘッドがはるかに大きくなります。

つまり、rom1v/delayは「省メモリだが、タイムスタンプの精度と粒度はチャンク単位（ミリ秒・最大4000バイト単位）」、tokideliのdelayは「メモリを多く使うが、バイト単位・ナノ秒単位の精度を持つ」という設計上のトレードオフの結果です。この違いが、tokideliのdelay.cが「物理メモリの80%を超えるサイズ指定を拒否する」という安全装置を持つ理由でもあります（1バイトを要求されるごとに実際には16バイト前後のメモリが必要になるため、指定サイズと実消費メモリの差が大きく、うっかり大きなサイズを指定するとメモリを使い果たしかねないからです）。

## あふれ処理の違い

rom1v/delayは、バッファが満杯になると常に標準入力の読み込みをブロックします（`poll_stdin`フラグを倒すことで実現）。これはtokideliのdelay.cの`-s`（Suspendモード、デフォルト）と同じ挙動です。

tokideliのdelay.cは、これに加えて`-o`（Overwriteモード：古いデータを捨てて新しいデータを優先）と`-d`（Disconnectモード：あふれた瞬間にバッファをすべて捨てて即時終了）も選択できます。また`-v`オプションで、あふれが発生したことを標準エラー出力に報告する機能もあります。rom1v/delayにはこれらの選択肢や可視性はありません。

## 実行中のパラメータ変更

rom1v/delayは起動時に指定した遅延時間・バッファサイズを実行中に変更する手段を持ちません（変更するには再起動が必要です）。

tokideliのdelay.cは、`controlfile`という仕組みで、実行中でも遅延時間・バッファサイズを変更できます。通常ファイルなら0.1秒ごとにポーリング（`SIGHUP`を送れば即時反映も可能）、キャラクタ・スペシャルファイルや名前付きパイプなら書き込み次第即時反映という、柔軟な運用が可能です。

## 移植性・規格適合性

rom1v/delayの`Makefile`には`CFLAGS += -Wall -g -O3`のみで、OSごとの条件分岐は見当たりません。これは必ずしも「他OSで動かない」ことを意味しませんが、少なくともソースコード上では複数OSへの明示的な対応は行われていないようです（未検証）。

tokideliの`delay.c`（および他の全16コマンド）は、Linux、Solaris 11.3、FreeBSD 12.1、NetBSD 7.0.2、OpenBSD 6.5、macOS 15.8、Android上のLinuxという7環境で実機ビルド・動作確認を行い、各OS固有の`feature_tests.h`の癖（Solarisの`__EXTENSIONS__`、FreeBSDの`_XOPEN_SOURCE`要件など）に対応しています。

また、rom1v/delayのGitHubリポジトリには、未解決のissueとして["Undefined behavior"](https://github.com/rom1v/delay/issues/5)が上がっています。`dtbuf.c`内でヘッダー構造体へのポインタを、アライメントが保証されていないバイト配列上の任意の位置にキャストしてアクセスしている箇所が、厳密には未定義動作（[x86でのデータアライメントに関するバグの実例](http://pzemtsov.github.io/2016/11/06/bug-story-alignment-on-x86.html)と同種の問題）である、という指摘です。これは2026年時点でも未修正のまま残っています。

## まとめ

rom1v/delayは、単一の目的（一定時間の遅延）に特化した、小さく完結したツールです。メモリ効率が良く、シンプルで理解しやすい反面、実行中の設定変更やあふれ時の挙動選択のような運用面の柔軟性は持たず、タイムスタンプもチャンク単位・ミリ秒精度に留まります。

tokideliのdelayコマンドは、バイト単位・ナノ秒精度の遅延計算、複数のあふれ処理モード、実行中のパラメータ変更、幅広いOSへの対応など、より高機能・高精度・運用しやすい設計になっていますが、その代償としてメモリ消費量は指定サイズよりもかなり大きくなります。どちらが優れているというより、**想定する使用場面（軽量な用途か、精度・柔軟性が必要な用途か）によって適切な選択が異なる**、という結論になります。
