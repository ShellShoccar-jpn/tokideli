# valveコマンドの転送レート精度に関するレポート

(English version is [here](valve_precision.info.en.md))

## 概要

本レポートでは、データ転送レート制限コマンド[valve(1)](valve.man.ja.md)の精度について、次の2つの観点から検証する。

1. 同種の有名なレート制限機能を持つ`pv`コマンド（`-L`オプション）とのソースコード比較・実測比較に基づく、valveコマンドの設計上の優位性
2. 一般的なスペック・一般的なUNIX系環境において、valveコマンド自身にも避けられない誤差要因と、その実測値

すべての実測は、[linets(1)](linets.man.ja.md)コマンドの`-9 -d`オプション（各行にナノ秒精度のタイムスタンプと、直前の行からの経過時間"delta-t"を付与する機能）を用いて行った。

### 実験環境

| 項目 | 値 |
|---|---|
| CPU | AMD Ryzen 7 7735HS with Radeon Graphics |
| 論理コア数 | 16 |
| カーネル | Linux 6.18.33.2-microsoft-standard-WSL2（WSL2、PREEMPT_DYNAMIC） |
| valveのビルド | `cc -O3 -o valve valve.c -pthread -lrt` |
| pvのバージョン | 1.11.0（同一環境でビルド） |

WSL2はWindows上の軽量仮想マシンの中で動くLinuxカーネルであり、ホストOS（Windows）のスケジューラによる追加の抽象化層を持つ。したがって、後述する誤差の値は、素のLinux環境よりもやや大きめに出ている可能性がある点に留意されたい。

## ①　pvコマンドとの比較によるvalveコマンドの優位性

### 設計上の違い

[valve(1)](valve.man.ja.md)と`pv`の`-L`（レート制限）は、いずれも「一定のレートでデータを送出する」という同じ目的を持つが、そのタイミング制御の方式が根本的に異なる。

#### valve: 絶対時刻ベースのスケジューリング

valveは、`spend_my_spare_time()`関数（`c_src/valve.c`）の中で、次のように「次に送出すべき絶対時刻」を直接計算し、その時刻に対して`nanosleep()`する。

```c
/*--- Calculate "tsTo", the time until which I have to wait ------*/
ui8 = (uint64_t)tsPrev.tv_nsec + gi8Peritime;
tsTo.tv_sec  = tsPrev.tv_sec + (time_t)(ui8/1000000000);
tsTo.tv_nsec = (long)(ui8%1000000000);
```

ここで重要なのは、送出後に`tsPrev`（基準時刻）を更新する際、**実際に起きた時刻ではなく、理論上の予定時刻（`tsTo`）を使う**という点である。これにより、`nanosleep()`が多少オーバースリープしても、その誤差が次回以降に累積することがない。さらに、オーバースリープが続いた場合に休止時間を短縮して遅れを取り戻す「リカバリーモード」も備えている。精度を決めるのは、実質的に`nanosleep()`自体の分解能だけである。

#### pv: ポーリング型・離散トークンバケット方式

一方、pv 1.11.0のソースコード（`src/pv/loop.c`, `src/pv/transfer.c`）を分析すると、`-L`によるレート制限は次のように実装されている。

```c
#define RATE_GRANULARITY 100000000  /* nsec between -L rate chunks */
...
while (pv_elapsedtime_compare(&cur_time, &next_ratecheck) > 0) {
    rate_limited_target += rate / (1000000000.0 / RATE_GRANULARITY);
    pv_elapsedtime_add_nsec(&next_ratecheck, RATE_GRANULARITY);
}
cansend = (off_t)(rate_limited_target);
```

送信可能量は**100ミリ秒単位**でしか更新されない、階段状のトークンバケットである。さらに、実際に「送信可能になったこと」を検知する仕組みは、次の`select()`呼び出しに依存する。

```c
n = is_data_ready(check_read_fd, &ready_to_read, check_write_fd, &ready_to_write, 90000);
```

このタイムアウトは**90ミリ秒**に固定されている。加えて、pvは入力側の読み込みをレート制限と無関係にバッファが満杯になるまで先読みする設計のため、パイプ経由で大量のデータが即座に流し込まれる状況（後述の実験がまさにこれに該当する）では、バッファが速やかに満杯になり、以後は「バッファ満杯かつ送信枠なし」の状態で`select()`が監視対象fdなしで呼ばれ、実質的に**90ミリ秒周期のポーリングタイマー**として機能することになる。

つまりpvの送出タイミングは、「100ミリ秒周期のトークン補充」と「90ミリ秒周期のポーリング」という、互いに協調しない2つの粗い周期の組み合わせによって決まる。この非同期な組み合わせがうなり（ビート）を生み、平均レートは正しくても、個々の送出タイミングには周期オーダーのジッターが生じる。

#### 設計上の違いのまとめ

| | valve | pv（`-L`） |
|---|---|---|
| 方式 | 絶対時刻ベースのスケジューリング | ポーリング型・離散トークンバケット方式 |
| タイミング決定 | 次に送出すべき絶対時刻を直接計算し、その時刻に対して`nanosleep()`する | 100ms粒度のトークン補充と、90ms周期の`select()`ポーリングの組み合わせで決まる |
| 誤差の蓄積 | 基準時刻を理論上の予定時刻で更新するため蓄積しない（オーバースリープ分もリカバリーモードで解消） | 二つの粗い周期が非同期に絡み合い、うなり（ビート）状のジッターとして現れる |
| 理論上の精度上限 | `nanosleep()`と`clock_gettime()`自体の分解能に漸近する | 100msのトークン粒度と90msのポーリング周期に律速される（最大で概ね100〜190ms程度のオーダー） |

### 実測比較

以下のコマンドを用いて、1行/秒のレートでの精度を実測した（60行、約60秒間）。

```sh:
$ seq -f '%05.0f' 1 60 | valve 48bps | linets -9 -d
$ seq -f '%05.0f' 1 60 | pv -qL 6   | linets -9 -d
```

（"48bps"は1文字=8bitとして換算した6 Bytes/sec、"pv -qL 6"も同じく6 Bytes/secであり、いずれも6文字の行（例："00001\n"）を1秒に1行送出する設定である。`-q`はpvの進捗表示を抑制するオプション。）

各行の直前行からの経過時間（delta-t、linetsが付与）を、期待値である1000msからの偏差として集計した結果は次のとおり。

| | valve 48bps | pv -qL 6 |
|---|---:|---:|
| サンプル数 | 59 | 59 |
| 平均間隔 | 1000.0019 ms | 999.9394 ms |
| 間隔の標準偏差 | **0.288 ms** | **3.573 ms** |
| 最大偏差（絶対値） | **1.069 ms** | **7.704 ms** |
| 平均偏差（絶対値） | 0.187 ms | 2.868 ms |

標準偏差・最大偏差ともに、valveはpvよりおよそ**一桁（10倍以上）精度が高い**という結果になった。これは前節で述べた設計上の違い——valveの絶対時刻ベースのスケジューリングと、pvの粗いポーリング周期に依存したトークンバケット方式——が、そのまま実測値に表れたものと考えられる。

## ②　valveコマンド自身の精度限界

とはいえ、valveも万能ではない。`nanosleep()`と`clock_gettime()`という、OSが提供する時刻管理機構に依存している以上、一般的なスペック・一般的なUNIX系環境で運用する限り、マイクロ秒〜サブミリ秒オーダーの誤差は避けられない。主な要因は次のとおりである。

* **`nanosleep()`自体の分解能限界**: Linuxの高分解能タイマー（hrtimer）は数マイクロ秒オーダーの分解能を持つが、それはあくまで「起床要求のタイミング」の精度であり、実際にプロセスが再開されるタイミングとは別問題である。
* **スケジューラの介入**: `nanosleep()`から目覚めても、他のプロセス（特に高優先度のもの）がCPUを使用中であれば、実行が遅延する。CFS（Completely Fair Scheduler）のタイムスライス粒度もこれに影響する。
* **コンテキストスイッチのオーバーヘッド**: プロセスの休止・再開そのものに、数マイクロ秒〜数十マイクロ秒のオーバーヘッドが伴う。
* **割り込みレイテンシ**: ハードウェアタイマー割り込みの処理には、CPUの省電力状態からの復帰などにより、数十マイクロ秒の遅延が生じることがある。
* **CPU周波数スケーリング（DVFS）**: 省電力クロックから通常クロックへの遷移に時間がかかる場合がある。
* **仮想化のオーバーヘッド**: 今回の実験環境であるWSL2のように、ゲストOSのスケジューラの上にさらにホストOSのスケジューラが介在する環境では、追加のジッターが生じ得る。
* **測定手法自体の誤差**: 計測に用いたlinets自身も`clock_gettime()`呼び出しとフォーマット処理を行っており、その処理時間そのものがごくわずかに計測結果へ加算される。

### 実測

以下のコマンドで、より短い周期（10ミリ秒、1ミリ秒）における実際の揺らぎを計測した。

```sh:
$ seq -f '%05.0f' 1 500  | valve -l 10ms | linets -9 -d
$ seq -f '%05.0f' 1 1000 | valve -l 1ms  | linets -9 -d
```

| | 周期 10ms | 周期 1ms |
|---|---:|---:|
| サンプル数 | 499 | 999 |
| 平均間隔 | 10.0008 ms | 1000.05 μs |
| 間隔の標準偏差 | 254.06 μs | 28.74 μs |
| 最大偏差（絶対値） | 860.18 μs | 246.89 μs |
| 平均偏差（絶対値） | 170.32 μs | 19.20 μs |

実行結果の抜粋（10ms周期、`linets`が付与したタイムスタンプと直前行からの経過秒数）:

```text:
20260906013151.427904104 0 00001
20260906013151.438012167 0.010108063 00002
20260906013151.447994354 0.009982187 00003
20260906013151.458026325 0.010031971 00004
20260906013151.468087135 0.010060810 00005
```

この結果から、次のことが読み取れる。

* 絶対的なジッターの大きさ（最大偏差にして概ね数百マイクロ秒程度）は、周期の長さによらずおおむね似た範囲に収まっている。これは、ジッターの主な原因がOSのスケジューリング・割り込み処理に起因する固定的なノイズであり、valveの周期計算ロジック自体の問題ではないことを裏付けている。
* したがって、周期が短くなるほど、この固定的なノイズの**相対的な**影響は大きくなる（10ms周期では相対誤差最大約8.6%、1ms周期では相対誤差最大約24.7%）。ミリ秒未満の非常に短い周期でシビアな精度を要求する用途には、OS標準のタイムシェアリングカーネル上で動く一般的なアプリケーションという制約上、限界があることに留意されたい。
* 一方、①で示した1秒周期のような、比較的長い周期においては、この固定的なノイズの絶対量（最大約1ms程度）は相対誤差にすると0.1%程度に収まり、実用上ほぼ問題にならない精度を達成している。

## まとめ

* valveは、pvのような「粗いポーリング周期に依存するレート制限」とは異なり、次に送出すべき絶対時刻を直接計算して`nanosleep()`する設計により、同一環境下でおよそ一桁高い精度を達成している（1秒周期の実測で標準偏差0.288ms対3.573ms）。
* ただし、valveの精度も、OSのスケジューラや割り込み処理に起因する数百マイクロ秒オーダーの固定的なノイズからは逃れられない。この固定的なノイズは周期の長さによらずほぼ一定であるため、短い周期ほど相対誤差が大きくなる。実運用では、要求される精度と周期の長さのバランスを踏まえた上で使用することが望ましい。
